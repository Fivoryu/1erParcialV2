- S4 Multiplicity RANGE with numeric bounds (e.g. 2..5) end-to-end (assumption: nullable lower/upper bound columns).
- S4a Contract for S4 (decided by parent, assumption). `MultiplicityKind.RANGE` stays the discriminator. Attributes and relationship ends gain nullable ints `lowerBound`/`upperBound` (DB cols `lower_bound`/`upper_bound`, migration `V32__multiplicity_range_bounds.sql`, additive; backfill legacy RANGE rows to 0..*). RANGE => `lowerBound` required (>=0); `upperBound` null = unbounded (`*`), else `>= max(lowerBound,1)`. Non-RANGE => both must be absent/null else INVALID_PAYLOAD; switching away from RANGE clears them. Payload fields on attribute.add/update and on relationship end objects (source/target) in relationship.create/update: `lowerBound`, `upperBound`. Resources (AttributeResource, RelationshipEndResource) expose the same two fields (JSON null when unset); old snapshots without the fields read as null. Notation: `2..5`, `2..*`, `3` when lower==upper.
- S5 Stereotypes on classifiers, attributes, operations, rendered as «name».
- S5a Contract for S5 (user decision L5: "Una lista, ya que el usuario común no va a entender como hacerlo al menos que sea un profesional": a FIXED list chosen from a selector, never free text). One stereotype per element (assumption). Storage follows the existing relationship pattern (V27): nullable `stereotype VARCHAR(32)` on `uml_classifier`(check real table name), `uml_attribute`, `uml_operation` in migration `V33__member_stereotypes.sql`; allowed names enforced by command handlers via Java enums (like `DependencyStereotype`), not DB CHECKs. Lists: classifier (only kinds CLASS and ABSTRACT_CLASS; interface/enumeration keep their own label, package none): ENTITY, BOUNDARY, CONTROL, SERVICE, UTILITY, TYPE, AUXILIARY, FOCUS, IMPLEMENTATION_CLASS, METACLASS, SIGNAL. Operation: CREATE, DESTROY, QUERY. Attribute (modeling conventions, not UML-standard; easy to trim): ID, UNIQUE, READONLY. Payload: `attribute.add/update` and `operation.add/update` accept `stereotype` (string|null; null clears); classifier uses a NEW command `classifier.stereotype.set` with payload `{ "stereotype": string|null }`, target classifier; `classifier.create` also accepts `stereotype`. Unknown name => INVALID_PAYLOAD; wrong classifier kind => INVALID_PAYLOAD. Resources expose `stereotype` (null when none; old snapshots read null). Display: `«entity»` lower-case guillemets via existing `formatStereotype`; classifier: above the name; member: prefix before the member text. UI: select with "(ninguno)" plus Spanish label + term (e.g. "Entidad «entity»"). Generation ignores stereotypes. AI plan/assistant support is out of scope for T3.
- S6 Notes (entity, canvas node, link, XMI ownedComment).
- S6a Contract for S6 (decided by parent after user delegated: "Cual debería hacerlo?"; follows UML `Comment.annotatedElement` 0..*). A note is a model-level entity (`uml_note`, migration `V34__notes.sql`, additive) with `id`, `body` (non-blank, max 2000), plus join table of annotated elements (target type CLASSIFIER|RELATIONSHIP, target id; 0..N links, no duplicates; links to deleted elements are removed with them). Commands: `note.create` {body, annotatedElementIds[]}, `note.update` {body}, `note.delete`, `note.link` / `note.unlink` {targetType, targetId}. Notes appear in ModelResource (`notes: [{id, body, annotatedElements:[{targetType,targetId}]}]`; old snapshots read empty), snapshots/VCS merge, undo, ModelStateHasher (append only when non-empty), SchemaOwnershipTest columns. Notes have canvas geometry through the existing view element_geometry (new target type NOTE; check how geometry targets are validated). XMI: `ownedComment` with `annotatedElement` idrefs in EA dialect; unknown refs dropped with a loss entry. UI: add-note tool, note node (folded-corner rectangle, wrapped body text), dashed link edges to annotated elements, editing the body and link/unlink in the properties panel. Generation ignores notes. AI plan support out of scope.
- S7a Contract for S7 (decided by parent, assumption; user said "Si" to continue with stage 5). Facts: operations already have `isStatic`; attributes have no static/derived; relationship ends have no ordered/unique. Migration `V35__attribute_flags_and_end_properties.sql` (additive): `uml_attribute.is_static`, `uml_attribute.is_derived` boolean NOT NULL DEFAULT false; relationship-end table `is_ordered`, `is_unique` boolean NOT NULL DEFAULT false (check real table names). Payload: `attribute.add/update` accept booleans `isStatic`, `isDerived`; relationship end objects (source/target) in `relationship.create/update` accept booleans `isOrdered`, `isUnique`; non-boolean => INVALID_PAYLOAD; omitted on update = unchanged. Resources expose the four fields (false when unset; old snapshots read false). Semantics (assumption): `isUnique` false means "not marked" (no notation), true shows `{unique}`; `isOrdered` true shows `{ordered}`. Notation: static attribute underlined; derived attribute prefixed `/` (`/edad: int`); end properties as `{ordered}`/`{unique}` text next to the end multiplicity. XMI: `isStatic`/`isDerived` attributes on the attribute element, `isOrdered`/`isUnique` on the end property, EA dialect; write only when true; reader accepts them. Also pick up VCS merge, undo, snapshots, ModelStateHasher (append only when a flag is true so old hashes stay), SchemaOwnershipTest columns. Generation ignores them. UI: checkboxes "Estático", "Derivado" for attributes and "Ordenado", "Único" for each relationship end in PropertiesPanel; canvas rendering per notation. AI plan support out of scope.
- S7 Derived `/`, {ordered}/{unique} ends, static attributes (assumption).
