# Mobile client and authenticated generated-backend gateway

Objective: deliver a Flutter mobile client that authenticates with the platform, selects a generated backend, and uses an on-device agent to propose database operations executed through an authenticated gateway.
Branch: `codex/mobile-local-ai-gateway`. Delivery strategy: `ask-on-risk`; chain strategy: `feature-branch-chain` (accepted by “dale”; local commits only, no publishing). Test runners: backend Maven tests; Flutter tests once the scaffold exists. Forecast: over 400 authored changed lines across four work units, excluding generated Flutter scaffold files.

## Specs

S1. The mobile application implements: “Donde se hara login”. Authentication uses the existing platform login contract and stores the session using mobile secure storage rather than browser storage. Acceptance: a valid account reaches backend selection; invalid or expired credentials remain unauthenticated with an observable error. Checks: repository/service tests and Flutter authentication flow tests.

S2. After login, the user can “seleccionar el backend generado y conectarse con dicho backend”. The selected target is a deployment owned through an accessible platform project. The mobile client connects only through the user-selected authenticated platform gateway; it never receives permission to call an arbitrary URL. User clarification: “El celular podrá conectarse a diferentes backends. Pero solo uno.” and “Con uno me refiero que también puede salirse del backend y entrar en otro”. Acceptance: accessible generated deployments can be listed, exactly one is active at a time, and the user can leave it and select another; unavailable or unauthorized deployments are rejected without leaking connection details. Backend switching must not mix contracts, proposals or results between deployments. Architecture interpretation: leaving a backend is distinct from logging out of the platform. Checks: backend authorization and gateway contract tests plus Flutter selection/disconnection/switch-isolation tests.

S3. After connection, the user can “usar mi agente para añadir, crear, editar, etc. Sobre esa base de datos”. The agent targets generated-domain data, not the canonical UML assistant. It uses the generated backend contract for natural-language tools. User messages authorize unambiguous additions and edits; deletion requires a concrete preview and explicit confirmation, per S9. Preserve legacy explicit-confirmation API behavior until the additive agent operation contract is verified. Acceptance: at least one domain-generic read/create/edit flow works without hard-coding the examination domain; rejected proposals make no data change. Checks: public-interface gateway tests, Flutter proposal/confirmation tests, and a vertical contract scenario.

S4. The local AI requirement follows CU-22: Flutter runs a device-local runtime independently of the backend runtime, using the required Qwen 3.5 0.8B identity. The exact artifact, runtime, quantization, preprocessing, and target hardware remain a technical-validation dependency until verified. No remote result may be presented as local. Acceptance: the agreed interaction produces an observable proposal with networking disabled, reports model/runtime/latency, and preserves pending local state when gateway synchronization cannot complete. Checks: runtime capability probe on target hardware, offline Flutter test seam, and reconnect/idempotency tests where applicable.

S5. User-selected architecture decision: “Gateway autenticado”. Every generated-data request is authenticated at the platform, authorized against project/deployment access, constrained to the selected generated contract, and audited. Acceptance: missing, expired, cross-project, arbitrary-host, unsupported-operation, and contract-mismatch requests fail without forwarding. Checks: focused security tests and independent verification because this is high-risk security and public-contract work.

S6. User requested: “Hay alguna manera de poder cargar el módelo rapidamente en vez  de estar escribiendo de forma manual?” and “Además que no me gusta tener una sola pantalla, quiero que sea minimalista y fácil de entedner”. Accepted flow: Login, Backends, Agent, and separate Settings; detect the already-installed app-private model and offer Load AI without manual paths. No new download or personal-storage permission is authorized. Checks: deterministic discovery/loading states, navigation/draft retention and explicit confirmation regressions.

S7. User accepted implementation: “Vale, no te olvides de añadir botones para ir hacia atrás para que la navegación sea más fácil de hacer”. Child screens expose Back; Back retains session/connection/model/draft, while explicit Leave backend and Sign out retain their distinct existing effects. Checks: actual router back, missing-backend guard, logout and model-loading race.

S8. Conversational UX: “Pare, porque no parece un chat real lo que has hecho, la petición que hiciste es muy técnico y no lo quiero así.” “Quiero que la IA local actue como agente que sea capaz de darme datos, borrar, calcular, etc.” “Con lenguaje natural sin necesidad de decir que llame un endpoint.” “Como un chat tipo gpt donde pueda inicar conversaciones y ver el historial. Un dia podría estar diciendo que me añada algo y otro día quiera calcular algo complicado.” Account synchronization chosen: “Sincronizarlo”. “1. Si hacemos que al entrar a un backend pueda ver su historial solo de ese backend. Si entro a otro solo veo del B.” “2. Cada chat es una nueva sesion para el agente.” Acceptance: private account-owned backend-scoped conversations, stable IDs/idempotent message synchronization, history/new-chat/continuation UI, isolated contexts with no hidden remote inference. Existing project collaboration chat must not be reused.

S9. Confirmation policy: “Antes de borrar”. Reads, calculations, unambiguous additions and edits may proceed from the user's request without a second confirmation. Every deletion must preview exact targets and require user confirmation tied to that intent. Ambiguous requests ask for clarification. Existing permissions, contract validation and unknown-write guards remain enforced. Checks: rejected/foreign intents cause zero forwarding; automatic additions/edits do not authorize model-generated unrelated actions.

S10. Generic backend agent: “Recuerda que dicha IA estará lista para cualquier base de datos, si lo ponemos solo para ello no podrá hacerlo si ejecuto otro backend totalmente diferente”. Acceptance: domain-independent tools derive entities/fields/allowed operations from each selected compatible frozen contract; no inventory/sales-specific logic, arbitrary URLs, SQL or generated executable code. Safe deterministic calculations use available validated data and disclose missing inputs, coverage and assumptions. Tests use at least two unrelated entity shapes; actual local-model capability is measured, never assumed from mocks.

S11. Offline persistence: “4. Si esta bien conservar, pero también como es local quiero poder añadir datos y que se guarde en sqlite y que este listo para cuando regrese el internet para sincronizar los cambios.” Cached reads/calculations accepted: “Si quisiera hacer eso.” Automatic saving of consulted data plus optional dataset download accepted: “Si me gustaría guardar los datos.” Account/platform/backend/contract-scoped SQLite stores history/cache/outbox atomically. Queued offline additions synchronize only to their original authorized backend after reconnect; known rejection/conflict/unknown results stay pending with explanation, without overwrite, silent discard or blind retry. Conflict policy accepted: “Sip”. No offline edit/delete authorization. Cached answers disclose fetchedAt/coverage and pending versus committed data; unavailable/oversized data must not be reported as complete. Migration only creates new structures; preserve existing data.

S12. Resources and progress: “Vale, como el modelo no tiene mucha pontencia, también debemos medir cuanto tiempo y potencia usará ya que si le pido algo complicado se detendrá”. Budget: “Unos 5 min”. “Me gustaría poder ver su pensamiento para ver que realmente esta avazando en algo sin estar esperando a que solo me de una respuesta”. Acceptance: roughly five-minute absolute per-request budget across model/tool steps, bounded work, cancellation that stops future dispatch, truthful observable task/tool progress (not raw internal reasoning or invented percentages), elapsed model/tool timings and available own-process CPU/memory/thermal readings. Energy unavailable is explicitly unavailable, not fabricated. Already-dispatched writes are not rolled back by cancellation. Native cancellation requires real capability proof, not queued release. Tests cover deadline/cancel before dispatch and late completion fencing.

S13. Implementation authorization: “Dale”. Harness override after unavailable model: “Si usalo” authorizes gpt-6.1-sol/low for ODD workers. Preserve own USB app/user0 synthetic fixture scope; no personal data, publishing or remote execution. Work-unit commits remain pending chain strategy before first commit.
