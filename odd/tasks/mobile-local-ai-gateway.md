# Mobile client and authenticated generated-backend gateway

Objective: deliver a Flutter mobile client that authenticates with the platform, selects a generated backend, and uses an on-device agent to propose database operations executed through an authenticated gateway.
Branch: `codex/mobile-local-ai-gateway`. Delivery strategy: `ask-on-risk`; chain strategy: `feature-branch-chain` (accepted by “dale”; local commits only, no publishing). Test runners: backend Maven tests; Flutter tests once the scaffold exists. Forecast: over 400 authored changed lines across four work units, excluding generated Flutter scaffold files.

## Specs

S1. The mobile application implements: “Donde se hara login”. Authentication uses the existing platform login contract and stores the session using mobile secure storage rather than browser storage. Acceptance: a valid account reaches backend selection; invalid or expired credentials remain unauthenticated with an observable error. Checks: repository/service tests and Flutter authentication flow tests.

S2. After login, the user can “seleccionar el backend generado y conectarse con dicho backend”. The selected target is a deployment owned through an accessible platform project. The mobile client connects only through the user-selected authenticated platform gateway; it never receives permission to call an arbitrary URL. User clarification: “El celular podrá conectarse a diferentes backends. Pero solo uno.” and “Con uno me refiero que también puede salirse del backend y entrar en otro”. Acceptance: accessible generated deployments can be listed, exactly one is active at a time, and the user can leave it and select another; unavailable or unauthorized deployments are rejected without leaking connection details. Backend switching must not mix contracts, proposals or results between deployments. Architecture interpretation: leaving a backend is distinct from logging out of the platform. Checks: backend authorization and gateway contract tests plus Flutter selection/disconnection/switch-isolation tests.

S3. After connection, the user can “usar mi agente para añadir, crear, editar, etc. Sobre esa base de datos”. The agent targets generated-domain data, not the canonical UML assistant. It uses the generated backend contract for natural-language tools. User messages authorize unambiguous additions and edits; deletion requires a concrete preview and explicit confirmation, per S9. Preserve legacy explicit-confirmation API behavior until the additive agent operation contract is verified. Acceptance: at least one domain-generic read/create/edit flow works without hard-coding the examination domain; rejected proposals make no data change. Checks: public-interface gateway tests, Flutter proposal/confirmation tests, and a vertical contract scenario.

S4. The local AI requirement follows CU-22: Flutter runs a device-local runtime independently of the backend runtime, using the required Qwen 3.5 0.8B identity. The exact artifact, runtime, quantization, preprocessing, and target hardware remain a technical-validation dependency until verified. No remote result may be presented as local. Acceptance: the agreed interaction produces an observable proposal with networking disabled, reports model/runtime/latency, and preserves pending local state when gateway synchronization cannot complete. Checks: runtime capability probe on target hardware, offline Flutter test seam, and reconnect/idempotency tests where applicable.

S5. User-selected architecture decision: “Gateway autenticado”. Every generated-data request is authenticated at the platform, authorized against project/deployment access, constrained to the selected generated contract, and audited. Acceptance: missing, expired, cross-project, arbitrary-host, unsupported-operation, and contract-mismatch requests fail without forwarding. Checks: focused security tests and independent verification because this is high-risk security and public-contract work.
